GitHub link: https://github.com/KingsleyMatthew/cse341-books/blob/main/src/db/connect.js

5.b. How did you store sensitive data? Why is that approach important?

Answer: I stored the MongoDB connection string in a local .env file as MONGODB_URI and never wrote it in the code. In src/db/connect.js, the app reads it with process.env.MONGODB_URI and throws 'MONGODB_URI is required.' if it’s missing. The dev and start scripts in package.json load the file with --env-file=.env, and .gitignore lists .env so it never reaches GitHub. My spec planned this too: its security section says to keep credentials in environment variables only, and its error rules say clients never see connection strings or database details. In the deployed app, I set MONGODB_URI and MONGODB_DB_NAME in Render’s environment settings instead of uploading a .env file.

This approach is important because the connection string includes my database username and password. If it were committed, anyone who could see the repository could read or change my data, and removing it later doesn’t erase it from Git history. Keeping it in the environment also lets the same code use different databases locally and in production.

6.a. Include a GitHub link to a file that shows one other implementation decision you made.

GitHub link: https://github.com/KingsleyMatthew/cse341-books/blob/main/src/models/books.js

6.b. What decision does this file show, and why did you make that choice?

Answer: src/models/books.js shows my decision to control exactly what the database returns. Both getAllBooks() and getBookById() use { projection: { _id: 0 } }, so MongoDB’s internal _id never leaves the model, and getAllBooks() also sorts with .sort({ title: 1 }). The issue only said to use find({}) and findOne({ id: bookId }). I added these because my Version 2 spec says each book has only id, author, title, and publicationDate, and that list order should be predictable. Without the projection, the API would return a fourth field that clients don’t need and that exposes internal database details. Without the sort, the order of /books could change between calls. In the deployed app, GET /books returns the three seed books in the same title order every time, with no _id. The choice keeps the API response matching the spec, so a client developer can rely on it.
