## Plan vs. Implementation

5. Which part of the work took more or less time than expected? Why?

Answer: Writing the spec took longer than I expected, and implementing the routes took less. The spec took time because I had to make design decisions myself, such as 409 for duplicate ids, blocking an author’s delete while books still reference them, and how PUT handles an id in the body. Once those were written down with exact error messages in the GitHub issues, the controllers and routes went quickly because I was just following my own checklist. Swagger took longer than expected for one reason: after I added the new author routes, /api-docs still showed only GET /authors. The cause was that swagger.json is only rebuilt when I run npm run swagger, so I learned to regenerate it and restart the server after changing route comments.

6. How did Swagger help you in your work this week?

Answer: Swagger let me test my API from the browser without writing any extra code or using another tool. For each route I could click Try it out, paste a request body, and see the status code and response right away. That made it easy to check the cases in my Test Plan, such as a 409 for a duplicate id, a 400 for an invalid birthYear or an unknown authorId, and a 404 for a missing book. Writing the @openapi comments also forced me to compare each route with what the controller really returns, so the docs and code had to match. The same page worked on my deployed Render app, so I could test the deployed API the same way I tested it locally.
